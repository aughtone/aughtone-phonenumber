# Alphabetic input in parsing: extension markers over vanity folding

ADR-0002 · 2026-09-20 · Status: accepted
Keywords: vanity numbers, alpha numbers, 1-800-FLOWERS, keypad conversion, letters folded into number, unrecognised extension label, foreign extension word, poste, ramal, anexo, allowVanityNumbers, ALPHA_NUMBER_DISALLOWED, extensionMarkers, caller-provided markers, why is my parsed number wrong, extension dropped, opt in to vanity, #23, #24, #26

## Context

Parsing keypad-converts any run of three or more letters into digits, matching upstream libphonenumber (`1-800-FLOWERS` → `1-800-3569377`). Inside a byte-stable normalizer whose output feeds token derivation, that automatic conversion produces a **wrong number that still validates** — the worst failure shape here, because a token derived from it silently identifies the wrong line, or fails to match a token that should have matched, and nothing reports it. It reaches the default path in two ways.

**An unrecognised extension label folds into the subscriber number.** The built-in localised label set is a partial list. A label inside it is stripped correctly (`+1 212 555 0123 anexo 4` → `+12125550123` ext `4`); a label outside it is not, so its letters go through keypad conversion and land in the number: `+1 212 555 0123 poste 4` → `+12125550123767834`, no extension captured ([#26](https://github.com/aughtone/aughtone-phonenumber/issues/26)). `poste` (French) and `ramal` (Portuguese) have no entry; `Durchwahl` and `interno` fold the same way and are only caught, when they are, by the length check. The set cannot be completed — a list of the word "extension" in every language is unbounded, and every gap yields a wrong number rather than a refusal — so extending the list is not a fix, and inviting downstream to copy it only works if it is complete.

**A stray alphabetic word folds the same way.** `1-800-FLOWERS` is the intended case, but any incidental word in otherwise-numeric input — a pasted label, `CALL`, `HELP` — becomes digits in the number just as silently.

This is the same shape as [#22](https://github.com/aughtone/aughtone-phonenumber/issues/22), [#23](https://github.com/aughtone/aughtone-phonenumber/issues/23) and [#24](https://github.com/aughtone/aughtone-phonenumber/issues/24): the answer is wrong rather than absent. Downstream adoption (`aughtone-normalize`) worked around it by refusing every localised label and rejecting ASCII letters before calling `parse` — direct evidence that the safe posture is to not fold unknown alphabetic input.

Constraints already in force (ADR-0001): compat mode stays byte-identical to upstream (the parity anchor); default mode may do the more-correct thing; output is a pure function of `(input, flags)`, never a global. One more force is specific to timing: a change in publishing process means the next release will be a long time coming, so the default behaviour has to be as correct as it can be **now**, not documented now and corrected later.

## Decision

In default mode, `parse` no longer keypad-folds alphabetic input into the national number. A run of letters is resolved by **validity** — the same principle used for the American `#` form in #24:

- **Letters after a number that is already valid without them are an unrecognised extension marker.** Recognising a bare word as a marker is a heuristic, not a vocabulary — it reads `0123 asdfgh 9` as readily as `0123 poste 4` — so the default is conservative: the marker **and its trailing digits are dropped**, leaving the correct number with **no extension** (`+1 212 555 0123 poste 4` → `+12125550123`, no extension). This never produces a wrong number and never invents one. A caller who wants best-effort extraction opts in with the per-call `allowUnknownExtensions: Boolean = false`; when `true`, the trailing digits are taken as the extension (`… poste 4` → ext `4`). This resolves #26 structurally, with no word list — the fold that produced a wrong number is gone either way; #23 and #24 are the same principle for a no-digit marker and the American `#`.
- **Letters the number needs in order to be valid are a vanity (alpha) number, and are refused by default.** `parse` throws the port's own `ErrorType.ALPHA_NUMBER_DISALLOWED`, distinct from `NOT_A_NUMBER`, so a caller can tell "this was a vanity number you can opt into" from "this was garbage." A caller opts in with the new per-call `allowVanityNumbers: Boolean = false`; when `true`, the letters keypad-convert as before, still inside the corrected default mode. `isValid` takes the same flag and returns `false` for a vanity number unless it is set.
- **Callers with known data can supply markers.** A new per-call `extensionMarkers: Set<String>? = null` on `parse` adds to the built-in label set (matched case-insensitively) and is stripped before the validity check. It makes a known input format deterministic and covers the one case the validity heuristic cannot — an extension on a base that is not independently valid, e.g. a local number `1234 poste 5` → `1234` ext `5`.
- **The discarded run is visible.** When the default drops an unrecognised marker, `PhoneNumber.droppedText` holds the raw run removed (the marker and its trailing digits), so a caller can tell "no extension" from "an extension was discarded" and return to the source — the same reason we require the region rather than guess it. Null otherwise; never in `formatToE164()`. With `allowUnknownExtensions` on, the digits become the extension instead and nothing is recorded as dropped.
- **Formatting characters are recognised as widely as the input, and marker detection is script-agnostic.** A run of letters in any script (Latin, Cyrillic, CJK, fullwidth, accented) after a valid number is treated the same way, so the fold is not an ASCII-only fix. The dash and separator classes are a frozen set whose non-ASCII members replicate upstream's `VALID_PUNCTUATION` exactly, so a Unicode dash (U+FF0D, U+30FC), a no-break or zero-width space, or a fullwidth paren — from autocorrect, CJK, or a web/PDF paste — is never misread as a marker (which would drop real digits) and a dash typed for a hyphen is never missed as the Durchwahl signal (which would fold a wrong number, [#29](https://github.com/aughtone/aughtone-phonenumber/issues/29)). Replicating upstream's set is what keeps compat byte-identical here.
- **Compat mode is unchanged.** `libphonenumberCompat = true` folds vanity and unrecognised labels exactly as upstream; none of the new parameters (`allowVanityNumbers`, `allowUnknownExtensions`, `extensionMarkers`) alter it. The explicit utilities `convertAlphaCharactersInNumber` and `isAlphaNumber` are also unchanged — a caller invokes those deliberately.

**Rejected: extend the built-in label set with `poste`, `ramal`, and the rest.** Fixes named inputs and leaves the shape intact — the next unlisted word folds. No complete multilingual list exists, and each new recognised marker shifts where the number ends, itself a called-out byte change. It treats a structural defect as missing data.

**Rejected: document the fold as a deliberate divergence and change nothing.** Cheap and byte-stable, but it leaves the silent-wrong-number footgun in the default path — the outcome we most want to avoid — to match an upstream behaviour default mode already departs from elsewhere. With no near-term release to correct it later, shipping a known footgun as the default is the wrong trade.

**Rejected: fix the extension case but keep folding true vanity by default.** This is the structural fix without the vanity policy; it closes #26 but leaves `1-800-FLOWERS` and every stray word silently converted. Refusing by default is the safer posture for a token-deriving normalizer, and the opt-in keeps the capability for callers that want it.

**Rejected: gate vanity conversion on `libphonenumberCompat`.** Reuses an existing flag, but conflates "reproduce upstream exactly" with "allow vanity," so a caller wanting corrected default behaviour *with* vanity conversion could not have it. A separate `allowVanityNumbers` keeps the two knobs orthogonal.

## Consequences

**Easier.** The default path no longer emits a silently-wrong number from a stray word or a foreign extension word — the #22/#23/#24 family is closed at its root, #26 needs no word-list maintenance, and the default never invents an extension from an unconfirmable marker. A vanity refusal is legible (`ALPHA_NUMBER_DISALLOWED`), so a caller can branch on it — retry with `allowVanityNumbers = true`, or reject — rather than discovering a wrong number later.

**Harder.** Three new per-call parameters (`allowVanityNumbers`, `allowUnknownExtensions`, `extensionMarkers`) and a new `ErrorType` widen the public surface; an exhaustive `when` over `ErrorType` in a consumer must add the branch. The validity-based split costs a second validity check at parse time on inputs that contain letters. A caller that relied on default-mode vanity folding must now pass `allowVanityNumbers = true`, and one that wants an extension read from an unrecognised marker must pass `allowUnknownExtensions = true`.

**What changed in output.** Default-mode E.164 changes for inputs containing alphabetic runs — previously folded to a wrong-but-valid number, now reduced to the correct number (an unrecognised marker and its trailing digits dropped, no extension invented) or refused (a vanity number). This is a called-out default-mode change. Compat output is untouched, so a consumer pinned to compat is unaffected, and the folded 0.0.3 outputs for these inputs were not values worth preserving.

**The unknown-marker opt-in is a heuristic, not a vocabulary.** Under `allowUnknownExtensions`, `0123 asdfgh 9` yields extension `9` as readily as `0123 poste 4` — it never yields a wrong number, but it can read an extension from input nobody can confirm. That is exactly why extraction is opt-in and the default drops. (Surfaced in downstream review right after the decision, 2026-09-20; it confirmed the conservative default rather than changing the decision.)

**Reviewed before landing.** A cross-review (a peer reviewer plus the downstream consumer `aughtone-normalize`) caught two defects in the first cut: gating the whole block on `allowVanityNumbers`, which re-folded unrecognised labels and made `isNumberMatch` miss; and a formatting set narrower than the input, which would drop real digits on a Unicode separator and, in the Durchwahl guard, fold a wrong number on a fullwidth hyphen ([#29](https://github.com/aughtone/aughtone-phonenumber/issues/29)). Both are fixed. The lesson, recorded because it recurs: a character class must be as wide as the input it is applied to, or the result validates and the error is silent.

**Downstream.** A consumer that previously guarded against the silent fold no longer needs that guard — the library produces the correct number itself and, by default, reports no extension it cannot confirm. A consumer that wants extensions read from unrecognised markers opts in per call; one that wants none never sees an invented split. Canary tests pinned to the old folded output flip when this ships, by design.
